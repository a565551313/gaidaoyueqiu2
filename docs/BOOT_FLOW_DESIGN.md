## 一、目标与原则

按主流网游（端游：更新→选服→登录；手游：登录→选服）的开机套路，给游戏加一条**仪式感的启动链路**：

```
LOGO 展示 → 检查更新/读取资源 → 选择服务器 → 登录/注册 → 主菜单
```

四条设计原则（全部来自项目现状，不是空话）：

1. **回访要快**：老玩家从冷启动到主菜单 **< 3 秒**。所有可以跳过的页面都要能自动跳过
   （LOGO 限时、单服自动过、自动登录），仪式感只给第一次和主动查看的人。
2. **离线永远可玩**：启动链路任何一步断网，都提供「离线继续」出口——本地存档 + 打包默认内容包
   就是完整单机（这是 Phase 0/1 已打好的底）。云端挂了只会降级，不会拦人。
3. **游客优先，无注册墙**：现架构是 Supabase 匿名登录（玩家无感）。登录页必须保留
   **一键游客进入**，邮箱注册是可选增强，绝不能变成强制门槛。
4. **进度不丢**：现有玩家（包括你自己）都是匿名账号。登录页的核心能力之一是
   **匿名 → 邮箱账号升级绑定**（Supabase `updateUser`），本地进度原样带走；
   登录账号与本机进度冲突时，复用已有的 LWW+保底合并（`merge.js`）。

## 二、总流程与状态机

### 2.1 完整链路（首次启动 / 手动退出登录）

```
┌─────────┐   ┌──────────────┐   ┌─────────────┐   ┌──────────────┐   ┌────────┐
│ P1 LOGO │──▶│ P2 检查更新   │──▶│ P3 选择服务器 │──▶│ P4 登录/注册  │──▶│ 主菜单  │
│ 1.2~2.0s│   │ 资源读取      │   │（单服自动过） │   │（记住则自动过）│   │        │
└─────────┘   └──────────────┘   └─────────────┘   └──────────────┘   └────────┘
                    │                                                        │
                    │ 离线/失败                                               │ 点击头像/设置
                    ▼                                                        ▼
              「离线继续」──────────────────────────────────────────▶ 同一链路可回访
```

### 2.2 回访链路（目标 < 3s）

```
LOGO（1.2s，点击即跳）→ 更新页（并行预载，通常 <1s，无新版本直接过）
  → 上次服务器（唯一服 → 跳过选服页，只在更新页角标显示 800ms 服务器名）
  → 自动登录（游客：匿名会话恢复；账号：持久会话 supabase-js persistSession）
  → 主菜单
```

### 2.3 状态机（App.vue 内新增 boot phase）

```
phase: 'splash' → 'update' → 'server' → 'auth' → 'game'(现有 route.name='menu' 起)

转移条件：
  splash  → update    ：定时到 / 点击跳过 / 音频解锁成功（先到者）
  update  → server    ：资源就绪 && 服务器清单就绪 && 需要选服（无记忆或多服）
           → auth     ：资源就绪 && 单服 && 无有效会话
           → menu     ：资源就绪 && 单服 && 有效会话（自动登录）
           → offline  ：用户点「离线继续」（phase 直接进 game，云端状态 off）
  server  → auth      ：选定服务器（写记忆）
  auth    → menu      ：登录成功（游客/邮箱/注册/绑定升级）
  game ↔ server       ：主菜单「点击头像 → 切换服务器」回访该页（换服=换云端，进度按本地+云端合并）
```

**顺序采用「选服在登录前」**（端游套路，也是你点名的顺序）：服务器决定登录到哪个 Supabase
项目，登录动作必须发生在选服之后，技术上更顺；与手游「登录后选服」的差异在
**单一服务器时完全无感**（自动跳过），两种顺序的 UX 成本相同。

### 4.2 步骤行状态机

每行四态：`待定 ○ → 进行中 ◐（呼吸动画）→ 完成 ✓（青色）→ 失败 ✗（红，附【重试】按钮）`。
失败行可单独重试；全部失败也不阻断——底部按钮切换为「**离线继续**」。

### 4.3 进度的真实数据源（不造假进度条）

| 步骤 | 数据源 | 现状映射 |
|---|---|---|
| 检查版本 | `GET {CDN}/app-config.json`（§7），比较 `latestVersion` 与 package.json version | **新**；无配置/失败 → 视为「已是最新」（离线兜底） |
| 连接服务器 | 选定服务器的 Supabase URL 健康检查（`auth.getSession()` 计时） | supabaseAdapter 已有连接逻辑，包装成状态行 |
| 读取资源 | `preloadSpritePacks()` 的图集加载计数（Kenney 粒子/星空包，1.1MB） | 现在在 `main.js` fire-and-forget，改为可观测 |
| 云端会话 | supabase-js `persistSession` 恢复：游客有会话 → 「✓ 游客已恢复」直接放行；无会话 → 「○ 待登录」→ 进 P4 | CloudSync.init 拆分（§8） |

> 强更（`version < minVersion`）：步骤行显示「✗ 需要更新」，主按钮变「前往更新」——
> Web 游戏即提示「请刷新页面获取最新版本」或跳应用商店（打包 App 的未来槽）。当前恒不触发，仅留槽。

### 4.4 合规槽（国内发行需要，先占位）

- 底部链接：**用户协议 / 隐私政策 / 客服**（`docs/legal/` 占位文档 + P2 页链接；首次登录需勾选，见 P4）。
- 健康忠告（「适度游戏益脑」）可加在 LOGO 页角落，`BOOT_CONFIG.showHealthNotice` 开关控制，默认关。

### 5.2 服务器卡信息

每张卡：**名称（大）· 状态点（绿=流畅/黄=拥挤/灰=维护）· 标签（推荐/新服/火爆）· 本机进度标记**。
状态由 `app-config.json` 的 `servers[].status` 远端驱动（不是前端猜的）。

### 5.3 「服务器」在本游戏的真实语义（关键决策）

当前只有一个 Supabase 项目，"服务器"要诚实设计，分三层：

| 层 | 语义 | 现状 |
|---|---|---|
| **现在** | 一个服务器 = 一个 Supabase 项目（URL+anonKey）。单服（「澄河都会 · 一区」= 你的 sptaayelyiqrbppgvjcv 项目） | 页面上线即用，单服自动跳过 |
| **开发自用** | 再配一个 staging Supabase 项目 = 「测试服」。切换 = 换 URL/key + 重新握手，开发/线上数据隔离 | 随时可加（好处很大：不再拿生产库调试） |
| **未来多区** | 玩家分区/渠道区（排行榜与社交隔离） | 配置驱动，加一行即开区；跨区数据不互通是 MMO 常规，云存档按服存（`saves` 表在各自 Supabase 里，天然隔离） |

**单服时不显示本页**（自动选择 + 更新页角标闪现服务器名 800ms）；从主菜单「头像 → 切换服务器」
永远可达。多服时首次必显，之后默认进上次服，右上角「切换」常驻。

### 6.2 四条核心流程

| 流程 | 行为 | 技术映射 |
|---|---|---|
| **游客进入** | 匿名会话（现状）→ 直接进主菜单；游客也能云同步 | `signInAnonymously()`（已有） |
| **账号登录** | 邮箱+密码 → 恢复会话 → **拉云端存档与本机合并**（LWW+保底）→ 主菜单 | `signInWithPassword()`；`mergeSave()` 复用 |
| **注册** | 昵称+邮箱+密码+协议勾选 → 注册即登录 → 昵称写入 `players.display_name` | `signUp()` + 新 RPC `set_display_name`（SQL 0002，玩家可改自己的昵称，RLS 不放开直写） |
| **游客转正（绑定）** | 游客 tab 下小入口「绑定邮箱，永久保存进度」：邮箱+密码+昵称 → **当前匿名账号原地升级**，本地/云端进度原样保留 | `updateUser({ email, password })`——Supabase 匿名升级；这是给你自己现有进度留的转正通道 |

### 6.3 状态与校验

- 表单校验全部**前端即时**（失焦触发）：邮箱格式、密码 ≥8、昵称 4~12 字、两次密码一致、协议勾选。
- 服务端错误翻译成人话：`Invalid login credentials` →「邮箱或密码不正确」；`User already registered` →「该邮箱已注册，试试登录或找回密码」；`Email not confirmed` →「请先到邮箱点击确认链接」（Supabase 默认关邮箱确认，我们配置为**关闭**，注册即生效，休闲游戏别折磨玩家）。
- 登录成功动效：按钮变「✓ 执照核验通过」→ 400ms → 月星扩散转场进主菜单。
- **登录/绑定过程中本机进度永不删除**：合并策略就是现有 `mergeSave`（星级/最高分/材质保底不回退），哪怕登录的是另一台设备玩过的老账号。

```jsonc
    { "id": "chenghe-1", "status": "smooth" }
  ]
}
```

### 7.4 SQL 0002（新增迁移：昵称）

```sql
-- 玩家自助改名（RLS 未放开 players 直写，走 RPC；每分钟限 1 次防刷）
create or replace function public.set_display_name(p_name text)
returns boolean language plpgsql security definer set search_path = public as $$
declare uid uuid := auth.uid();
begin
  if uid is null then raise exception 'not authenticated'; end if;
  if length(trim(p_name)) not between 4 and 12 then raise exception 'bad name length'; end if;
  update public.players set display_name = trim(p_name) where id = uid;
  return found;
end; $$;
```

（注册流程的昵称即首次 `set_display_name`；排行榜/管理后台读 `display_name` 的链路已存在。）
